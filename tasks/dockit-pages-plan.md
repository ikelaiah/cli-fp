# Implementation Plan: cli-fp DocKit GitHub Pages site

> **Superseded architecture decision (v1.4.3, 2026-09-11):** The completed
> single-version site described below was correct for its original v1.4.0
> scope, but is no longer the active publishing model. cli-fp now uses DocKit
> historical/versioned documentation: every published release is built from
> its immutable release source, so readers can select documentation aligned
> with that release tag. The original decision is retained as historical
> context; do not restore single-version Pages or remove `docs/versions.json`.

## Overview

Adopt DocKit `v1.0.0` as the repository's documentation site builder, using
the existing root `README.md` as the homepage and a curated set of current
guides under `docs/`. Keep runtime source and behaviour unchanged, preserve
historical repository material, and originally publish one current
documentation version from the default branch. That delivery was superseded by
the immutable historical-release model recorded above.

## Architecture decisions

- Use the released DocKit `v1.0.0` reusable workflow and command-line
  contract; never depend on DocKit `main`.
- Use the repository-root README as the explicit DocKit home because it already
  contains the project identity, hero asset, first CLI, and current v1.3.3
  behaviour. Repair its site-facing links rather than create a competing large
  introduction.
- Make `docs/layout.json` authoritative with `home`, `unlisted: "exclude"`,
  and hand-written sections. Publish only current reader, reference, example,
  generator, technical, and project pages that belong in the normal journey.
- Use built-in DocKit theme configuration and the existing cli-fp hero asset;
  rely on DocKit's built-in responsive Markdown image handling.
- Keep v1.4.0 roadmap ideas out of the supported API documentation. The
  class-based `TBaseCommand` API remains the documented current model.
- **Superseded:** Use the single-version Pages workflow generated by
  `dockit-fp github-pages`; do not add `docs/versions.json`. The active
  v1.4.3 decision instead uses the documented tag-triggered historical
  workflow and `docs/versions.json`.

## Risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Root README links target repository paths not published by DocKit | High | Run DocKit audit/build and make links point to published pages or external repository URLs. |
| Historical Markdown overwhelms navigation | Medium | Use explicit layout entries and `unlisted: "exclude"`; preserve files in place. |
| Documentation describes unreleased v1.4.0 ideas | High | Cross-check public claims against v1.3.3 source and label roadmap material as future work. |
| Theme or hero asset reduces contrast/readability | Medium | Prefer built-in preset/style, validate both light and dark modes and mobile layout. |
| Pages setting is not enabled for Actions | High | Check repository Pages state after merge; report the exact manual setting if API permissions cannot change it. |

## Definition of done

- The original curated single-version DocKit site was configured and locally
  validated with the released `v1.0.0` tool; the v1.4.3 migration supersedes
  it with a versioned, immutable-release site.
- Existing cli-fp runtime tests and CI workflow remain intact and pass.
- PR is merged, Pages deployment is green, and the live site is checked at
  `https://ikelaiah.github.io/cli-fp/`.

## v1.4.3 historical-docs migration

### Delivery plan

1. Add a schema-1 manifest for all verified release sources, using annotated
   tag refs where available and full commit SHAs for the older lightweight-tag
   release commits.
2. Use DocKit v1.0.0's documented tag-triggered reusable historical workflow.
3. Publish a new documentation-maintenance release because `check-release`
   requires the manifest current source to match the release `HEAD`; never
   rewrite the already published v1.4.2 tag.
4. Qualify `check`, `check-release`, and `build-all`; verify that oldest,
   middle, and current output has release-specific provenance.
5. Merge, create an annotated v1.4.3 tag, then verify the deployed selector
   and historical Pages routes.
